**Тема:** Domain-Driven Design (DDD): піддомени, bounded contexts та сутності

## 1. Опис предметної області

TaskTracker — навчальний вебзастосунок для перегляду й майбутнього керування навчальними завданнями. У практичній №1 реалізовано мінімальний варіант: браузер запитує `GET /items`, сервер Express читає таблицю `items (id, name)` у SQLite й повертає список.

У цій практичній моделюємо **майбутній розвиток**, не видаючи заплановані функції за вже реалізовані.

## 2. Піддомени та межі контекстів

| Піддомен / bounded context | Тип | Відповідальність | Власні сутності | Стан |
|---|---|---|---|---|
| Керування завданнями (Tasks) | Основний (core) | Створення, призначення, статуси, пріоритети і виконання завдань | `Task` | Мінімальна реалізація списку `items`; повне керування заплановане |
| Користувачі та доступ (Users) | Допоміжний (supporting) | Дані користувачів і ролі «студент» / «викладач» | `User` | Заплановано |
| Сповіщення (Notifications) | Загальний (generic) | Повідомлення про призначення та завершення завдань | `Notification` | Заплановано |

**Межі контекстів:** кожен контекст володіє своїми сутностями й правилами. Контекст `Tasks` зберігає лише ідентифікатор користувача (`assigneeId`), а не копію повного профілю; сповіщення отримують інформацію про події, а не керують завданнями.

## 3. Сутності та атрибути

### Task — навчальне завдання

| Поле | Тип | Значення |
|---|---|---|
| `id` | number або string | Унікальний ідентифікатор |
| `title` | string | Назва завдання, обов'язкова |
| `description` | string | Додатковий опис |
| `status` | `todo` / `in_progress` / `done` | Стан виконання |
| `priority` | `low` / `normal` / `high` | Пріоритет |
| `assigneeId` | string або null | Ідентифікатор призначеного користувача |

Методи: `assignTo(userId)`, `start()`, `complete()`. Правило: назва не може бути порожньою; завершене завдання не починається повторно.

### User — користувач

| Поле | Тип | Значення |
|---|---|---|
| `id` | string | Унікальний ідентифікатор |
| `name` | string | Ім'я |
| `role` | `student` / `teacher` | Роль у системі |

Метод: `canCreateTasks()` — у запропонованій моделі викладач може створювати завдання, студент — виконувати призначені.

### Notification — сповіщення

| Поле | Тип | Значення |
|---|---|---|
| `id` | string | Ідентифікатор |
| `recipientId` | string | Кому призначено |
| `message` | string | Текст повідомлення |
| `isRead` | boolean | Ознака прочитання |

Метод: `markAsRead()` — змінює стан сповіщення на прочитаний.

## 4. Взаємодія контекстів

1. `Users → Tasks`: Tasks отримує ідентифікатор і роль користувача, щоб призначити завдання та перевірити права (майбутня функція).
2. `Tasks → Notifications`: після призначення або завершення завдання Tasks передає подію на кшталт `TaskCompleted` (майбутня функція).
3. `Browser → Tasks → SQLite`: реалізований зараз шлях `GET /items`, який читає дані з таблиці `items`.

## 5. Прототип у коді

Файл [`domain/models.js`](../../domain/models.js) містить класи `Task`, `User` та `Notification` із полями й мінімальними методами. **Це прототип доменної моделі:** він поки не підключений до `server.js` і не змінює роботу вже реалізованого API.
